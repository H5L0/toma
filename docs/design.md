# Toma 设计：前因后果与目标

> 日期：2026-11-08。本文记录 Toma 的动机、设计目标与选型理由。具体计划和决策见[plans](plans/)、[ADR](adr/) 。

Toma 是一个多端通用智能助手：单一 Router 主控、Worker 执行任务、工作台呈现成果。

## 1. 设计目标

做一个**简单、易用、连续、通用**的助手，**智能、可视化地管理任务**。开发功能应该回答"是否增加心智负担、是否破坏连续性、是否只服务单一场景"。

| 目标 | 含义 | 落地 |
|---|---|---|
| 简单 | 减小心智负担：用户只需说事，不管会话、渠道等概念 | 单一主对话；主导航只有对话、任务；TomaApp 配置简单，点击即用 |
| 易用 | 随时可用、交互轻松 | 托盘常驻；可通过 PC、飞书、QQ 等多渠道直接沟通 |
| 连续 | 单一 Agent 主控：和你对接的总是熟悉的"它" | 唯一常驻 Router 面向用户；Worker 结束向 Router 结构化汇报；Prefilter 把新输入分派给现有 Worker 或 Router；不提供多主会话切换 |
| 通用 | 个人与团队都适用 | 个人用 TomaApp 单机内嵌；团队自托管 TomaServer；经插件接入群渠道、人格系统、工作节点等功能，随意拓展 |
| 智能、可视化地管理任务 | 任务是一等实体，进展与成果摆上工作台 | 每个任务对应一个 Worker：Ticket 下发目标与完成条件，WorkerReport 回收结果；任务视图聚合进展、审批与历史；成果以 Artifact 进入 Workbench，通过桌面窗口或在线网页展示 |

## 2. 选型前因后果

### 前因1：从 OpenClaw 与电话 App 出发

两条早期探索：

- **OpenClaw（新版 2.X）**：项目初期基于 OpenClaw 跑过多会话、工具调用、渠道接入和自动化。验证了"常驻 Agent + 从常用聊天渠道随时可达"是真实需求，也把问题暴露得很清楚。
- **电话 App**：语音通话式客户端探索，验证了语音是低负担、高表达的交互入口，但独立客户端形态没有解决"任务如何组织与呈现"。

确定需求是：**随时可达的入口、能做事的 Agent、看得见的任务**。

### 前因2：为什么放弃使用 OpenClaw

1. **无任务可视化**：核心仍是"聊天会话 + 工具循环 + 子Agent"，本质功能与 Claude Code/Codex + IM 通信 Hooks 没有差异，任务面板只展示任务三态，缺乏结构化和可视化。
2. **多人使用通过多 Channel 实现**：session 按消息来源路由，DM 共享主会话，不支持单一对话多人使用。会话与渠道耦合，上下文被渠道切碎，"同一个助手"的体验断裂。
3. **网页端非常粗糙**：Control UI 是纯 Vibe Code 产物，交互路径不清晰，控件样式不统一。
4. **功能杂乱且配置复杂**：OpenClaw 的 网关（Gateway）功能配置复杂、功能杂乱。用户需要理解"会话"、"渠道"、"工具"、"节点"等概念才能使用。

结论：问题不在底层 Agent 能力，而在上层缺少**任务模型及可视化设计 & 良好的交互体验**。这正是 Toma 要做的。

### 前因 3：DeepSeek Harness 团队发表《Super-agent》

- 文章提出 "Super-agent" 概念：一个常驻 Agent，跨渠道接收消息、调用工具、并行推进多任务——正是 Toma 的核心需求。
- 其实现思路是把渠道消息与自动化事件统一为 Trigger，再分派给会话处理，工程上无难点，验证了自建可行性。

### 前因 4：Anthropic 灰测 Claude Code Projects

- Anthropic 近期推出的"单会话 + 多任务"产品：一个协调会话把大项目拆成并行任务推进，获得广泛好评，验证了"单一主控 + 多任务"的产品形态。
- 但它仅对 Pro 及以上订阅开放，不对 API Gateway 用户开放，大多数团队无法依赖它进行开发——这一形态需要一个可自托管、无订阅门槛的实现。

### 前因 5：为什么改用 pi-agent

- 作者重度使用过 pi 的 CLI 版 并用 SDK 开发过 Agent，熟悉其行为、工具、数据存储与扩展方式，验证过可编程性。
- OpenClaw 底层同样是 pi-agent，证明其能力足以覆盖个人助手场景。
- pi 极简，内含会话、工具与上下文压缩等功能，同时在渠道、任务模型、权限与可视化方面留有自主设计空间，不受上游产品形态约束。

### 结果：基于 pi-agent + Router/Worker 重构 Toma

- 唯一常驻 Router（pi-agent * 1） 面向用户、理解意图并派发任务，每个任务对应一个上下文隔离的 Worker（pi-agent * N），结束后向 Router 提交结构化汇报。
- 渠道消息与自动化事件统一为 Trigger 进入系统。
- 任务进展与成果经任务视图和工作台可视化。
- 由此一并回应三个前因：补上 OpenClaw 缺失的任务模型与可视化，落地Super-agent 的常驻连续实体，提供 Projects 已验证但无法依赖的"单会话 + 多任务"。

## 5. 与同类产品对比

| 产品 | 形态 | 面向 | 部署与数据 | 亮点 | 缺点 |
|---|---|---|---|---|---|
| OpenClaw | 开源个人助手，Gateway + 多渠道 | 个人 | 自托管 | 渠道生态最广；pi-agent 内核，常驻助手形态成熟 | 多人会话按渠道切分、任务无实体、网页粗糙、Gateway 配置复杂 |
| Hermes（Nous Research） | 开源个人助手，持久记忆 + 自动技能 | 个人 | 自托管，模型自备 | 渠道覆盖广；隔离子 Agent 并行；技能可自动创建（自优化） | 以对话为主，任务可视化弱；团队协作弱 |
| Claude Tag | Slack 里 @ 的常驻 AI 队友 | 团队（Team/Enterprise） | Anthropic 云端 | 入口自然，@ 即委派；ambient 主动跟进；Claude Code 能力演化 | 绑定 Slack；可视化依托消息流；订阅门槛高 |
| Claude Code Projects | 协调会话 + 并行任务会话 | 个人/团队，编码中心 | Anthropic 云端 | 单会话主控，共享仓库、指令与记忆；大项目形态获好评 | 仅 Pro 以上订阅；会话列表可视化弱 |
| Codex dots | 云端常驻主动助手 | 个人/团队 | OpenAI 云端，订阅与地区限制 | 常驻主动推进，需决策才找人；可委派 Codex | 编码中心；可视化依托 ChatGPT 任务流 |
| Grok Bot | 常驻 Agent 团队，自有云电脑 | 个人/团队 | xAI 云端，X 付费订阅 | 24/7 常驻；多 Bot 并行分组；电脑控制能力强 | 绑定 Grok 模型；以对话为主，任务可视化弱 |
| **Toma** | 自托管服务端 + PC/Android App + IM Channels | 个人/团队，插件拓展 | 本地优先，模型自备 | 单Agent主控；多任务并行；多渠道；工作台可视化 | 渠道生态较少；插件系统未完善；Skills、MCP、记忆、安全等功能未实现 |

核心判断：

- **已被验证**：常驻、主动、跨渠道、从个人走向团队是行业共识，dots、Grok Bot、Claude Tag 都在做"always-on 队友"。
- **仍有缺口**：端侧产品（OpenClaw、Hermes）任务无实体、可视化弱；云端产品（Claude Tag/Projects、dots、Grok Bot）绑定自家云、订阅与地区，以编码为中心，数据离开本机，个人与小团队门槛高。

## 6. 未来路线图

按设计目标排序：先做透任务可视化，再完善插件系统，最后扩展入口与通用性。方向落地前先在设计文档定案，已有方案的直接链接。

### 近期：工作台成为协作主界面

- **物体协作**（[方案](plans/workbench-object-collaboration.md)）：工具执行自动记录触及文件、文件变更、命令记录与电脑控制轨迹，`present` 只负责补充和编排；用户选中任意物体即可讨论、要求修改或直接编辑；工作台按目标划分、汇集多个 Worker 的成果，Agent 改动实时高亮。消息历史退居旁白，从读聊天记录，变成围着物体协作。
- **补齐已知限制**：渠道文件收发、Worker 执行位置调整、文件型 Artifact 离线查看等当前边界逐项消除。

### 中期：完善插件系统

渠道、Worker 类型、人格系统等功能一律以插件实现（[插件系统](plugin-system.md)），核心只保留通用扩展点，不为单个功能开特例。

- **补齐运行期扩展点**：在渠道、Worker 类型、设置与静态上下文之外，增加事件观察、上下文注入、回复修饰、低频推进四个扩展点与插件独立数据目录；管理端配套插件设置、只读快照与数据重置（[设计决策](persona-system.md)）。
- **人格系统首个落地**：作为第一个扩展点消费者，验证接口足以支撑真实功能；此后新渠道与新 Worker 类型复用同一接口接入。

### 远期：入口与通用性扩展

- **插件生态**：渠道与 Worker 类型按需扩展，覆盖更多个人与团队场景。
